## Analysis

**The tasks cannot show a success gain.** grep + build solved all 90 of its runs. With the baseline at 100%, "+10
points of success" is out of reach whatever Farol does: these tasks, written so that a script can check them, are
within what Sonnet 5.5 does with grep, reading and a build.

**Farol's three failures were not wrong answers.** In `em02` (twice) and `em05` the answer was complete; the "changes
nothing" check failed because `src/ClientApp/Services/Basket/Protos/Basket.cs` and `BasketGrpc.cs` had been
rewritten. eShop's MAUI client generates its gRPC client into the source tree (`<Protobuf … OutputDir="">`), and those
files are committed. Loading the solution runs a design-time build, as Visual Studio does when it opens it, so
Grpc.Tools regenerates them and git reports both changed (the committed copies have CRLF line endings, which a
regenerated file need not keep); whether that happened before the grading depended on timing. Grpc.Tools' `DisableProtobufDesignTimeBuild` would prevent it, but would also leave the
gRPC types that other projects generate into `obj/` out of the compilations until a build, so Farol does not set it.
The agent never called Farol in these tasks: the load alone did it.

**Farol costs about 1,400 tokens per model call, used or not.** Its server instructions, the names of its 18 tools and
the skill's description are in the context of every call: the first call of a session reads 18.2k tokens with Farol
and 16.9k without. Over the 7 calls of an average session that is about 10k tokens, the 8% measured. A run that uses
Farol has to save that much before it saves anything.

**The agent used Farol in 49 of the 90 runs:** in 36 of the 45 fixture runs (every run of 11 of the 15 tasks), in 13 of
the 30 DNN Platform runs, and in none of the 15 eShop runs. When a few greps find the answer (`dm01`, `dg01`, `em01`), it does not load the
schema of an MCP tool to do the same.

**Where Farol replaced work, it saved tokens:** `lg04` (packages.config to PackageReference) −40%, `lm03` (a new
parameter through every caller) −17%, `md02` (vulnerable packages) −14%, `lm04` −13%. **Where it cost more,** it added steps or long answers: `dg02` +93%, `md03` +66%, `md04` +37%, `dm02` +35%.
Across the suite the agent called `dotnet_build` 31 times (about 1,000 characters per answer), `dotnet_find_references`
17, `dotnet_packages` 13, `dotnet_test` 12 and `dotnet_check` 11 (besides the hook's checks); the longest answers were
`dotnet_overview`'s, up to 33,000 characters on DNN Platform.

## What it means for the exit criterion

The criterion is the spec's, so what changes is the developer's decision. The levers the run shows:

- **The tasks.** A success gain can only show where grep + build fails: harder tasks (larger edits across projects,
  renames through markup and VB, behavior checked by tests), or the same tasks with a smaller model.
- **Farol's fixed cost.** Shorter server instructions and tool descriptions lower the 1,400 tokens every call pays;
  `dotnet_overview` could answer in less by default.
- **Being used.** In the tasks where the agent skipped Farol, it paid the fixed cost for nothing.

The raw runs (transcripts, checks, `summary.md`) are in `artifacts/evals/suite`, which is not committed.
