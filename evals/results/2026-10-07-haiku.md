## How the 30 tasks were chosen

There were 65 candidates. Thirty were the first suite's tasks. The other 35 were written for this purpose:

- on DNN Platform 10.3.3: the callers of one overload among same-named methods, or the code that writes one property;
- on Umbraco CMS 18.2.0, the benchmark corpus: the callers of one overload of a service interface.

The answers come from the compiler, not from Farol (`evals/oracle.ps1`): the member is marked `[Obsolete]`, the solution
is built, and every CS0618 or BC40000 warning is a use. Files that contain the same text without a use are decoys, and
an answer that lists one fails. Each new candidate was committed before it ran.

Each candidate ran twice with grep + build on Haiku: 130 runs, $14.25, not counted. A candidate that failed at least
once qualified, and qualified candidates were taken in task-id order up to 10 per job (`evals/select-calibrated.ps1`).

- **Maintain legacy:** 12 qualified; `xm09` and `xm10` were left out.
- **Migrate legacy:** 11 qualified; `xg14` was left out.
- **Modern .NET:** 11 qualified; `xu11` was left out.

On the first 30 tasks, Haiku with grep + build passed 55 of 60 runs, and only `lm01`, `lm03`, `lg02` and `lg03`
qualified. On the 35 new candidates it passed 17 of 70.

**Why the first attempt was stopped.** In its first runs, `dotnet_find_references` on
`ModuleController.GetModule(int, int, bool)` returned 16 calls, all inside `ModuleController.cs`. The compiler finds 93
calls in 47 files. DNN's callers reach the controller through `ModuleController.Instance`, which is typed as the
interface, so Roslyn files those calls under `IModuleController.GetModule`, and Farol dropped that group.
`dotnet_call_hierarchy` already included those calls. The spec now says what Visual Studio's Find All References does
(AC-37): a member's references include the uses through the interface members it implements and the members it
overrides, marked "via" that type.

The fix is commit `610ac21`. The measurement then restarted from its first run, with no other change to Farol. The
selection did not depend on Farol: calibration ran grep + build only.

## Analysis

**The gain comes from DNN Platform.** On its 16 tasks, Farol passed 40 of 48 runs and grep + build 13 of 48, at 143k
tokens per task against 401k. Each task asks for the callers of one overload, or the writers of one property, in 0.58M
lines of C# and VB. grep returns every same-named call; the agent then has to resolve overloads by reading. Haiku
stopped early, missed files or listed look-alikes.

With Farol, a `dotnet_find_references` call returns the compiler's answer. That tool accounts for 72 of the suite's 105
Farol calls, followed by `dotnet_find_symbols` (17) and `dotnet_symbol` (11). Across the suite, Farol-arm runs that used
Farol passed 45 of 54. Those that did not passed 8 of 36.

**On Umbraco, the agent barely used Farol.** It called Farol in 3 of 30 runs, all three in `xu07`, which passed 3 of 3
against 0 of 3. Umbraco's repository ships a 33 KB `CLAUDE.md` and its own skills, which both arms load. With them in
context, Haiku searched with grep and read files, and never loaded Farol's tools. On the other 9 tasks, both arms passed
3 of 27 runs, all in `xu03`. Getting the agent to use Farol in a repository whose own instructions steer it elsewhere is
open work.

**On the legacy fixture, Farol lost one task.** `lm01` asks for the names of the methods that call `GetTotal`. With
Farol, the agent listed call sites from `dotnet_find_references` and, in two runs, did not name the methods: 1 of 3,
against 3 of 3. The three edit tasks (`lm03`, `lg02`, `lg03`) came out even, 6 of 9 in each arm.

**Farol's fixed cost halved.** The first model call of a session reads a median 19.6k tokens with Farol and 18.9k
without, about 640 tokens more per call. Before the server instructions, the shared parameter descriptions and the skill
were cut, it was about 1,300 (measured with Sonnet, so the comparison is approximate).

## Threats to validity

**The oracle cannot see uses inside obsolete code.** The compiler does not warn about an obsolete member used inside
code that is itself obsolete, such as DNN's `[DnnDeprecated]` classes and Umbraco's `[Obsolete]` ones. A real caller
there is missing from the answer. If its text looks like a call, it also becomes a decoy that fails a correct answer.

Every decoy that an answer listed was checked against Roslyn's binding. Three are real uses inside deprecated classes:
`xm03` `Prompt/ModulesController.cs`, `xg03` `Users Online/UserOnlineController.cs` and `xu06`
`Packaging/PackagesRepository.cs`. The other cited decoys are genuine look-alikes:

- `Common/Globals.cs` aliases another `DataCache`;
- the project of `Reflection.vb` does not reference DNN's library;
- the Umbraco ones bind to extension methods or to the by-id overloads.

The recorded answers were re-graded under three gradings, after the re-grader first reproduced all 180 official grades:

| Grading | Farol | grep + build | Difference |
|---|---:|---:|---:|
| As measured (the criterion's) | 59% | 28% | +31 pts |
| The three real uses not penalized | 64% | 30% | +34 pts |
| No decoy ever penalizes grep + build (a bound) | 59% | 33% | +26 pts |

The criterion holds under each. The official result is the one measured.

**The tasks were selected on the baseline's failures.** Each task entered the set because grep + build failed it in
calibration, where it passed 10 of 60 runs. In the fresh runs it passed 25 of 90. Both arms ran on the same tasks with
fresh runs, but the gain describes tasks that are hard for grep + build with Haiku, not typical work: on the first 30
tasks, Haiku with grep + build passed 55 of 60.

**The model.** The model is Haiku 4.5, not Sonnet 5.5, under the rule fixed before any Haiku run. With Sonnet, grep +
build solved 100 runs of 100.

**One change to Farol between calibration and measurement.** The change is described above.

**What kind of task.** Of the 30 tasks, 27 ask which files call or write a member and have an exact answer, which is
Farol's strongest case. The 3 edit tasks came out even.

## What it means

The first exit criterion is met, with Haiku 4.5 on this task set. On a large legacy solution, compiler-accurate
references let a small model answer exact "who uses this" questions that it mostly fails with grep, for about a third of
the tokens.

The run does not show a gain:

- on edits;
- on typical tasks, where grep suffices;
- with Sonnet 5.5;
- in a repository whose own instructions keep the agent from using Farol (Umbraco).

The second exit criterion is the team using Farol on real projects for two weeks without blockers. That criterion and
AC-36 (manual smoke tests in Claude Code and Visual Studio 2026) are the developer's.

The raw runs (transcripts, checks, `summary.md`) are in `artifacts/evals/calibration-haiku`,
`artifacts/evals/suite-haiku-stopped` and `artifacts/evals/suite-haiku`, which are not committed.
