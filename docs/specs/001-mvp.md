## Problem

AI agents (Claude Code, Copilot, Cursor, Codex) work on .NET solutions with text search and `dotnet build`:

- grep cannot tell a definition from a usage, resolve overloads or find implementations;
- every `dotnet build` takes from 30 s to several minutes and dumps huge output into the context;
- agents guess the APIs of specific package versions (hallucination);
- legacy solutions (non-SDK .NET Framework projects, packages.config, VB.NET, WebForms/MVC 5, WCF/ASMX, WinForms/WPF) are ignored by existing MCP servers: roslyn-codelens skips non-SDK projects, almost all are C#-only, and Microsoft's modernize-dotnet agent only exists inside Copilot.

**Jobs the MVP serves (round 1):** all three, with equal weight in evals and priorities:

1. maintaining and evolving .NET Framework systems in production;
2. migrating legacy code to modern .NET;
3. day-to-day work on .NET 10/11.

**Success** is measured by evals against grep + build and by two weeks of real use (see Acceptance Criteria).

## Domain Model

- **Workspace** — one solution (`.sln`, `.slnx`, `.slnf`) or project, identified by its full path. States: not loaded → loading → ready | failed. Created on first request, loaded in the background, reloaded on project-file changes or `action='reload'`, disposed when the server exits.
- **Snapshot** — an immutable Roslyn `Solution` plus a version number. Every request runs on exactly one snapshot. Source edits produce a new snapshot; project-file edits trigger a reload.
- **Project** — a project file with its language (C#, VB), format (SDK-style or classic), target frameworks, output kind, app models, references and packages. A multi-targeted project is loaded once per target framework (round 4) and presented as one project listing its frameworks.
- **Document** — a source file (with a generated flag for designer and source-generator output). **Markup document** — an `.aspx`, `.ascx`, `.master`, `.svc`, `.asmx` or `.xaml` file, indexed for the code symbols it references (event handlers, code-behind classes, service classes, `x:Class`, named elements).
- **Symbol** — identified across calls by its documentation comment ID (e.g. `M:Legacy.Core.Orders.OrderCalculator.GetTotal(System.Int32)`). Tools accept a name, a dotted name, a documentation comment ID or `path:line`.
- **Diagnostic** — id, severity, location, message and the target frameworks it occurs in.
- **Baseline** (round 2) — the diagnostics of the load snapshot, computed per project the first time `check` needs it. A diagnostic is **new** when the baseline does not contain it. A reload resets the baseline. No git dependency.
- **Long operation** — load, build and test run as MCP tasks where the client supports the tasks extension; otherwise they run synchronously with progress notifications.
- **Legacy findings** — inventory item (technology, project, location, count), portability issue (API, technology, project, locations, suggested replacement) and migration plan (ordered steps with tasks).
- **Retention** — the MVP keeps no state on disk except what the user asks for: `migration_plan write: true` writes `docs/modernization/`, `code_actions apply: true` edits source files. Design-time loads write `obj/` like Visual Studio does.

## API Contract

### Conventions

- Tool names start with `dotnet_` and are in English, like their descriptions and outputs.
- **Output is compact text** built for the model (round 3), with paths relative to the workspace root (`path:line`, `/` separators).
- Every tool takes an optional `workspace` parameter (path to a solution/project or directory; default: discovered from the root), mirrored into the `Mcp-Param-Workspace` header.
- List-producing tools take `maxTokens` (default 1500, max 8000) and end truncated lists with "… N more". **(proposed)** They also take `offset` to continue a long list.
- Tool annotations: `readOnlyHint` on everything that does not write; `destructiveHint` on `code_actions` (apply) and `migration_plan` (write); `openWorldHint` on `package_api` and `packages`.
- Expected failures return an MCP tool error whose text says what went wrong and what to do next.
- **(proposed) Schema versioning:** tool schemas follow the package's SemVer (breaking changes only in a major version), guarded by a snapshot test of `tools/list`.

### Tools

| Toolset | Tool | Purpose | Key inputs |
|---|---|---|---|
| Workspace | `dotnet_workspace` ✅ | Load state, failed projects, toolchain | `action`: status · load · reload |
| Workspace | `dotnet_overview` ✅ | One-call solution map and working build command | `maxTokens` |
| Navigation | `dotnet_find_symbols` | Find declarations by name (camel-case and substring matching) | `query`, `kind`, `project`, `maxTokens` |
| Navigation | `dotnet_symbol` | Signature, documentation and optionally source of one symbol; skeleton for types; external symbols via SourceLink or decompilation | `symbol`, `include`: signature · docs · source |
| Navigation | `dotnet_find_references` | References grouped by project, including markup references and a member's uses through the interface members it implements or the members it overrides | `symbol`, `kinds`, `maxTokens` |
| Navigation | `dotnet_hierarchy` | Base types, derived types, implementations, overrides | `symbol`, `direction` |
| Navigation | `dotnet_call_hierarchy` | Callers or callees up to a depth | `symbol`, `direction`, `depth` |
| Navigation | `dotnet_outline` | Members of a file or type with signatures and lines, no bodies | `path` or `symbol` |
| Verify | `dotnet_check` | New diagnostics since the baseline, including in dependent projects | `scope`: changed · file · project · solution, `includeExisting` |
| Verify | `dotnet_code_actions` | List Roslyn fixes and refactorings at a location; preview as a diff; apply locally | `path`, `line`, `diagnosticId`, `action`, `apply` |
| Build & test | `dotnet_build` | Build with the right toolchain; errors deduplicated from the binary log | `project`, `configuration` |
| Build & test | `dotnet_test` | Run tests (all, filtered, or affected by a symbol or by changes); failures only | `project`, `filter`, `affectedBy` |

| Packages | `dotnet_package_api` | Public API of an exact package version, with XML docs | `package`, `version`, `query` |
| Legacy | `dotnet_legacy_inventory` | Legacy technologies with counts and hotspots per project | `project` |
| Legacy | `dotnet_config_inspect` | web.config / app.config contents, secrets masked, appsettings.json mapping | `path` |
| Legacy | `dotnet_portability` | APIs that do not exist in a target framework, grouped by technology, with replacements | `targetFramework` (default `net10.0`), `project` |

Behavior decided in round 3:

- **`code_actions`:** returns a unified diff by default. In local mode, `apply: true` writes the change atomically and returns a fresh `check` result. In remote mode it only returns diffs.
- **`migration_plan`:** returns the plan in the response. With `write: true`, it writes `assessment.md`, `plan.md` and `tasks.md` to `docs/modernization/` in the analyzed repository.
- **`package_api`:** looks up the exact version in the local NuGet cache first; when missing, downloads from the feeds in the solution's `nuget.config`, including private feeds through credential providers. `--offline` disables network access.

## Authorization

Loading a solution runs its code (MSBuild evaluation, analyzers, source generators); build and test run it too. Decided in round 4:

- **Trust:** Farol trusts the root directory the client started it in (Claude Code already asks the user to trust that folder). A solution outside the root loads only if its path is in `Farol:TrustedPaths`; otherwise the tool returns an actionable error.
- **Path sandbox:** every path a tool reads or writes must resolve inside the root or a trusted path, after resolving `..` and symbolic links.
- **Read-only mode:** write and execution are enabled by default in local mode. `--read-only` blocks `code_actions apply`, `migration_plan write`, `build` and `test`, and those tools explain why.
- **Secrets:** `config_inspect` masks connection-string passwords and secret-looking app settings.
- **Identity:** the caller context is the OS user in stdio mode, used for logging now and for authorization in the remote host (Phase 3).

## Edge Cases & Failure Modes

Decided in round 4:

- **Multi-targeted projects:** load every target framework; merge results that repeat per framework into one entry listing the frameworks. `Farol:TargetFrameworks` can limit loading.
- **Very large solutions:** accept a `.slnf` or a project filter in configuration, build compilations on demand, and warn in tool responses when managed memory passes `Farol:MemoryWarningMb`.

Proposed from the plan's principles:

- **Partial load:** projects that fail to load never fail the workspace; every response that depends on them lists them and why.
- **Still loading:** `workspace` answers immediately with progress; other tools wait for the load, as tasks where the client supports them.
- **Edits during a request:** each request runs on one immutable snapshot. Changes found by the file watcher, or by an mtime check before answering, produce a new snapshot for the next request.
- **Ambiguous symbol names:** return the candidates with their IDs instead of failing.
- **Unsupported projects** (F#, C++/CLI, `.sqlproj`, Web Site projects without a project file): listed as unsupported in `overview`, never a load failure.
- **No Visual Studio or Build Tools:** classic projects load with reduced fidelity, and `workspace`/`overview` say so.
- **Long processes:** build and test have configurable timeouts; on timeout or cancellation the whole process tree is killed.
- **Oversized results:** lists stop at the token budget and state how many items were left out and how to get them.

## Non-Functional Requirements

- **Performance (round 5, relaxed 2× from the plan; tightened in Phase 2 with the persistent index), measured by CI benchmarks:**
  - warm symbol queries: p95 under 100 ms;
  - `find_references`: p95 under 1 s on about 1M lines of code;
  - `check` after editing one file: p95 under 2 s;
  - memory: under 3 GB on about 1M lines of code.
- **Startup (proposed):** the server answers discovery and `tools/list` before any workspace finishes loading.
- **Platform:** legacy with full fidelity on Windows 10/11 with Visual Studio 2022+ or Build Tools. Modern projects also work on Linux and macOS. Requires the .NET 10 SDK.
- **Language (round 2):** everything in the repository is in English.
- **Privacy (proposed):** no telemetry is sent anywhere. Logs go to stderr; OpenTelemetry is opt-in. The usage log (AC-39) is opt-in too and stays on the machine.

## Integrations

- **.NET SDK:** `dotnet` for build, test and restore of SDK-style projects.
- **Visual Studio / Build Tools** (found with `vswhere`): `MSBuild.exe` for classic projects, `vstest.console.exe` for classic test projects.
- **NuGet** (round 3): local cache, then the solution's `nuget.config` feeds with credential providers; `--offline` flag.
- **Test frameworks (proposed):** xUnit v2/v3, NUnit, MSTest and TUnit, through VSTest and Microsoft.Testing.Platform, with results read from TRX.
- **Git (proposed):** not required in the MVP (the baseline is the load snapshot).
- **MCP clients (round 5):** validated in **Claude Code** (plugin, skill, hook, evals) and **Visual Studio 2026** (documented configuration and manual smoke test). **VS Code:** configuration documented but not validated in the MVP (review decision).
- **Distribution:** nuget.org and the Claude Code plugin. The MCP Registry listing comes in Phase 2.

### Verify

### Build & test

### Protocol, security and distribution

- **AC-29** — Every tool name starts with `dotnet_`, carries annotations, and its `workspace` parameter has `x-mcp-header: Workspace`.
- **AC-30** — Every path in every response is relative to the root and uses `/`.
- **AC-31** — The stdio host never writes anything but protocol messages to stdout.
- **AC-32** — Given a solution outside the root and not in `Farol:TrustedPaths`, when any tool targets it, then it fails with an actionable error.
- **AC-33** — Given the Claude Code plugin is installed, when the agent edits a `.cs` or `.vb` file, then the hook runs `dotnet_check` and the new errors reach the agent.
- **AC-34** — `dnx Farol.Mcp` starts the server from nuget.org; the package has the `McpServer` package type and a `server.json`.
- **AC-35** — The CI benchmarks meet the performance targets in Non-Functional Requirements.
- **AC-36** — Manual smoke tests pass in Claude Code and Visual Studio 2026.
- **AC-37** — Given a method that implements an interface member or overrides a base member declared in the solution, when `dotnet_find_references` runs on the method, then the uses through that member are included, each marked with the type it goes through, and the uses of the member's other implementations are not.
- **AC-38** — Given `--help`, `-h`, `-?` or `/?` among its arguments, when Farol starts, then it prints its version, how an MCP client starts it and every command-line option to stdout, and exits with code 0 without starting the server.
- **AC-39** — Given the usage log is on (`--usage-log`, or `Farol:UsageLog` from the environment or `appsettings.json`), when a client starts Farol and calls tools, then Farol appends one JSON line per event to a daily file under `Farol:UsageLogDirectory` (by default `Farol/usage` in the user's local application data): the session (Farol version, client name and version), each workspace load and warm-up (an 8-character hash of the solution's file name, duration, projects, load errors) and each tool call (tool, duration, outcome with Farol's error code, whether the token budget cut the response). It records no source text, argument values, paths or names, deletes its files after 30 days, and writes nothing when the option is off.
- **AC-40** — Given usage logs, when `farol --usage-report` runs (`--days N`, default 14), then it prints the days with use, the sessions and clients, each tool's calls, errors and p50/p95 durations, the errors by code and the loads per solution hash, and exits without starting the server.
