## Notes

- **Slice 1:** Roslyn 5.9 appends `~ReturnType` to every method's documentation comment ID. Farol normalizes IDs to the standard form (the suffix is kept only for conversion operators) and accepts both on input.
- **Slice 1:** Changes are applied lazily before the next request. Source edits update the snapshot in place, new files join SDK-style projects without a reload, and project-file changes reload. External (metadata) symbols have no source yet; SourceLink/decompilation lands with the packages slice.
- **Slice 3, `check`:** compiler diagnostics only; analyzer rules (CA/IDE) would cost seconds per check and come with `build` in slice 4. Edits that leave a file's declarations unchanged (top-level-equivalent syntax trees) re-check only the edited files; declaration changes re-check the project and every project that depends on it; `includeExisting` checks whole projects. A diagnostic is matched to the baseline by id, file, message and the text of its line, so line shifts do not make it new.
- **Slice 3, load snapshot:** Roslyn reads document text lazily, on first use, so a file edited before anything read it leaked into the load snapshot, which made the edit invisible both to file sync and to the `check` baseline. The loader now reads every document's text during the load.
- **Slice 3, `code_actions`:** Roslyn's built-in fixes and refactorings (`Microsoft.CodeAnalysis.CSharp.Features` and `VisualBasic.Features` 5.9), created by reflection. Actions that need a dialog are skipped. An optional `column` input, beyond the spec's key inputs, narrows refactorings to one position. `apply` refuses actions that change references or project files, refuses adding or removing files in classic projects (their project file lists every file), and refuses to write when the file changed on disk after the snapshot.
- **Slice 3, English output:** satellite resource assemblies are left out of the build (`SatelliteResourceLanguages=en`), so compiler messages and action titles are English on any OS language. MSBuild's own load messages can still follow the OS language; revisit with `build` and `test` in slice 4.
- **Slice 4, long operations:** the C# SDK (ModelContextProtocol 2.2) does not implement the tasks extension yet, so `build` and `test` take the spec's fallback: they run synchronously and send progress notifications. Revisit when the SDK ships tasks.
- **Slice 4, toolchains:** one classic project in scope means Visual Studio's MSBuild with `-restore -p:RestorePackagesConfig=true` (and `SolutionDir` when a single project is built); otherwise `dotnet build`. Builds and test runs of a workspace are serialized. Issues come from the binary log (MSBuild.StructuredLogger), with the console output as a fallback; binary logs and TRX files live in the temp folder, never in the repository, and the binary log path is logged rather than returned (AC-30). Compiler messages are English (`-p:PreferredUILang=en-US`, `DOTNET_CLI_UI_LANGUAGE`, `VSLANG`).
- **Slice 4, test hosts:** xunit.v3 4.x refuses VSTest-mode `dotnet test` on the .NET 10 SDK, so Microsoft.Testing.Platform is the main path for modern projects: the nearest `global.json` decides (`"test": { "runner": "Microsoft.Testing.Platform" }`). Classic projects run under `vstest.console.exe`; all three hosts take the same VSTest filter syntax (TUnit excepted) and report TRX (`--report-xunit-trx` for xUnit on the platform). Validated by running Farol's own tests through Farol.
- **Slice 4, affected tests:** references are followed backwards from the changed members (or a symbol) through enclosing members, interface members they implement and members they override, until test methods; only the test projects and their dependencies are searched, with a 3,000-symbol limit after which every test project that depends on the code runs. Test attributes are recognized by namespace and inheritance, and by name when packages are not restored yet.
- **Slice 4, fixtures:** `modern/tests/Modern.Tests` (xUnit v3, with `global.json` opting into the testing platform) and `legacy/Legacy.Tests` (classic MSTest through packages.config, which slice 5 reuses as its packages.config fixture).
- **Slice 5, `packages`:** reads what restore left on disk, with no MSBuild evaluation: the assets file (`obj/project.assets.json`, found next to the intermediate assembly, so the artifacts layout works) for PackageReference projects, `packages.config` plus the restored packages' manifests for classic ones (a package another installed package depends on is shown as "required by" it). Transitive packages carry the shortest chain from a direct package or referenced project. Without an assets file, the direct packages come from the project file and `Directory.Packages.props`. Vulnerabilities, deprecation and newer versions come from the feeds through the NuGet client (7.9): nuget.config, package source mapping, `auditSources`, the HTTP cache, credential providers (non-interactive). The optional `include` input filters (`direct`, `vulnerable`, `deprecated`, `outdated`).
- **Slice 5, `--offline`:** no network at all. `packages` then reports the vulnerabilities restore recorded in the assets files (NU1901–NU1904, read by code and URL because the message is localized), as it also does when no feed provides vulnerability data.
- **Slice 5, `package_api`:** the global packages folder and fallback folders first, then the solution's `packages` folder, then a download into the global packages folder exactly as restore does (so the tool still counts as read-only: it only fills a cache). The public API is read with Roslyn from the package's ref/ (else lib/) assemblies for one framework, compiled against the running runtime's framework assemblies so framework types display by name. An optional `targetFramework` input, beyond the spec's key inputs, picks the folder; the default is the framework of the project that uses the package, else the newest .NET one. Without a version, the version the workspace resolves, else the newest on the feeds.
- **Slice 5, external symbols in `symbol`:** the spec allows SourceLink or decompilation; decompilation (ICSharpCode.Decompiler, MIT) ships now, SourceLink is left for later. Reference assemblies have no bodies, so they are mapped to the implementation: the package's lib/ folder, the installed shared framework for targeting packs (following type forwarders into System.Private.CoreLib), the .NET Framework directory or GAC. External types get their public API as a skeleton, and their origin is named (package and version, or framework) without machine paths.
- **Slice 5, load issues:** MSBuildWorkspace reports every message of a design-time build as a failure, warnings included, and design-time builds replay restore's warnings: a project with a vulnerable package showed a load error. The loader now matches them with the assets file and reports warnings with their NuGet code. Paths inside load-issue messages are made relative to the root (AC-30). Build issues that restore reports against a project file are grouped under that project, not under the solution.
- **Slice 5, fixtures:** packages with published advisories and deprecations are pinned on purpose (`tests/fixtures/README.md`), and the package tests run against nuget.org.
- **Slice 6, API uses:** inventory, portability and the plan share one scan per project and snapshot: every name the semantic model binds to a type or member of a referenced assembly (a constructor counts as its type, an accessor as its property). Generated code (designer files, XAML and generator output, files marked auto-generated) is left out; the markup it comes from is counted instead.
- **Slice 6, `portability`:** exact rather than a list of known APIs: each .NET Framework API the code uses is looked up by documentation comment ID in the target's reference assemblies (the targeting packs under the .NET installation, or restored into the NuGet cache; netstandard2.0 comes from the NETStandard.Library package). Missing means the code will not compile; `[Obsolete]` on the target (SYSLIB0011 for BinaryFormatter, SYSLIB0024 for AppDomain.CreateDomain, WFDEV006 for dropped WinForms controls) is reported with its diagnostic and message. Projects that use WinForms or WPF are checked against the `-windows` surface. Package APIs are skipped: a package's own target frameworks decide. A small catalog (`LegacyCatalog`) only names the technology an API belongs to and the replacement to suggest.
- **Slice 6, `legacy_inventory`:** markup by extension (`.aspx`/`.ascx`/`.master`, `.asmx`, `.svc`, `.ashx`, Global.asax; XAML and Razor views when the project uses WPF or MVC), WinForms forms and user controls by base type, web.config/app.config facts, and catalog API uses with their lines; hotspots are the files with the most legacy lines. WinForms and WPF API calls are not counted (they run on `-windows`).
- **Slice 6, `config_inspect`:** secrets never leave the engine: passwords, keys and tokens inside connection strings (and connection strings kept in app settings), app settings whose names look secret, machine keys and identity passwords are masked. The appsettings.json mapping nests `A:B` keys as sections. Without `path`, the tool lists the workspace's configuration files (an extension to the spec's key inputs).
- **Slice 6, `migration_plan`:** steps follow project dependency levels, then libraries, tests, applications and web applications. Libraries and tests multi-target their .NET Framework version and the target; desktop projects retarget to `-windows`; System.Web applications get an incremental ASP.NET Core rebuild (YARP, System.Web adapters). Sizes: S converts, M replaces APIs or migrates packages.config, L rewrites a UI or service layer. `write=true` writes to `docs/modernization/` under the repository root (the nearest `.git` that Farol trusts), otherwise under the workspace directory; regenerating keeps the ticked boxes of `tasks.md`; project XML in tasks is wrapped in backticks so Markdown renderers show it.
- **Slice 6, fixtures:** `Legacy.Web/Web.config` gained the spec's password-bearing connection string, a secret-looking app setting (fake values) and an explicit WCF service with its endpoints.
- **Slice 7, package:** `Farol.Mcp` is a framework-dependent .NET tool (`RollForward=Major`) of package types `DotnetTool` and `McpServer`, with `.mcp/server.json` (MCP Registry schema 2025-10-17, used by nuget.org's MCP tab) and a package README with absolute links. MSBuildWorkspace's BuildHost folders ship inside it, so legacy solutions load from the package too. Clients run it with `dotnet dnx Farol.Mcp@<version> --yes` (`dotnet` rather than `dnx`, which is a `.cmd` shim on Windows that some clients cannot spawn); Farol's options go after `--`. A test packs the built host and starts the server from the package's own files; before the first release, the same was done through `dnx` with an isolated `NUGET_PACKAGES`, so no locally built version lands in the real NuGet cache.
- **Slice 7, plugin:** `plugins/farol` (manifest, `.mcp.json` running the pinned package, the `farol` skill, `hooks/hooks.json`), with this repository as its marketplace (`/plugin marketplace add yuriafp/Farol`). The hook is an `mcp_tool` hook: after Edit, Write or MultiEdit on `**/*.cs` or `**/*.vb` it calls `dotnet_check` on the plugin's own server with `format=hook` and `edited=${tool_input.file_path}`. The hook format answers in the JSON Claude Code reads (`decision: block` with the new errors, `additionalContext` for new warnings, `{}` otherwise, including while the workspace still loads), and `edited` applies the edit before checking, so the answer never races the file watcher. Verified headless in Claude Code 2.1.286 (`claude -p --plugin-dir`): the new CS0019 reached the agent as the hook's blocking reason. `claude plugin validate` passes for the plugin and the marketplace.
- **Slice 7, prompts:** the spec's prompts are MCP prompts served by Farol (`explore`, `verify_changes`, `upgrade_package`, `modernize`), so every client gets them; prompt arguments are strings, as MCP defines them.
- **Slice 7, contract:** the `tools/list` and `prompts/list` surface (names, annotations, parameters and whether they are required) is snapshotted in `tests/Farol.Tools.Tests/Snapshots/mcp-surface.json`; one version is repeated in six files, and a test keeps them equal. `docs/release.md` is the release checklist and `docs/smoke-tests.md` the AC-36 checklist.
- **Slice 8, benchmarks:** `benchmarks/Farol.Benchmarks` drives the real host over stdio on pinned corpora (`benchmarks/corpora`: Umbraco CMS 18.2.0, DNN Platform 10.3.3) and fails when a target of the spec is missed; `benchmarks/prepare.ps1` checks a corpus out and prepares it; `.github/workflows/benchmarks.yml` runs both. The first measurement on Umbraco missed two targets (symbol queries p95 556 ms, check p95 9 s), which changed the engine:
  - `find_symbols` scans each compilation's declaration table in parallel with its own matcher (`NamePattern`) instead of Roslyn's pattern search, which matched every declared name of the solution on each call.
  - `check` after a declaration change no longer compiles the edited project and every dependent whole. `DeclarationShape` compares the file's declarations before and after the edit from syntax alone, and `EditImpact` checks the files that use what changed: references of removed or changed members, files that name an added one (overloads, hiding, ambiguity), and the implementations an added abstract member needs. Changes a name cannot bound (type headers, operators, assembly attributes) still check the dependents whole, and so does a rewrite of more than 64 declarations. Files with syntax errors are checked alone.
  - Projects with no edits of their own bind against their load-time compilation pointed at the edited references (`Compilation.ReplaceReference`), so the workspace does not rebuild them and rerun their source generators, which took about 2 s per large project.
  - A file put back as it was at load makes the snapshot rebase on the load solution, which keeps its compilations.
  - After a load, a background warm-up builds every compilation and the reference and inheritance indexes.
  - `find_references` classifies references in parallel.
- **Slice 8, CI benchmarks:** on the runner's 4 cores, `find_references` missed its p95 on both corpora (1.32 s on Umbraco, 1.05 s on DNN) while every other target held. The slowest calls were always the first ones timed: the benchmark timed them while the server's background warm-up still ran, sharing the 4 cores. The benchmark now waits until `dotnet_workspace` reports the warm-up done (its duration is in the report), and the status shows it to agents too. Classifying each use also bound the code around it, which cost as much as the search itself (about 1 s for 1,500 uses of `IPublishedContent` on 4 cores): types are now classified from the syntax (created or referenced; as a receiver or a type argument a type used to come out as the member's read or call), and so are calls; the rest binds once per document. That classification test also showed a type's references left out where it is created, which Roslyn files under the constructors; they are now included as `new`. On 4 local cores `find_references` p95 went from 999 ms to 387 ms on Umbraco (348 ms on DNN). Job logs and summaries need a signed-in GitHub user, so the benchmark also reports its results as annotations, which anyone can read. With those fixes CI met every target on both corpora; the tightest was `check` on DNN (p95 1.82 s), the declaration edit of `FileManager.GetUrl`, whose name 23 files share. With more files to check than processors, a file's baseline (the file bound again as it was at load) is now only computed when the file has diagnostics now, since a file with none has nothing new; with fewer, it is still computed beside, on an idle processor. That edit went from 1.18 s to 0.73 s on 4 local cores.
- **Slice 8, after the first eval run:** Farol cost about 1,400 tokens per model call whether used or not, and two more turns in the sessions that loaded the skill and then the tool schemas. The server instructions went from 2,201 to 918 characters (about 320 tokens less per call), the skill's description from about 480 to 170 characters and its body from 5.4k to 2k (it is now the modernization playbook only, which the agent loads for that work), and the shared parameter descriptions got shorter. The harder task set follows the selection rule recorded in the spec's process log before any of its runs.
- **Slice 8, the harder tasks:** their answers come from a compiler oracle (`evals/oracle.ps1`: the member marked obsolete, every warning a use), the list tasks are generated with decoys (`evals/new-list-task.ps1`), and the set is selected from a calibration (`evals/select-calibrated.ps1`). The first measurement runs exposed a gap in `dotnet_find_references` (uses through implemented interface members, now AC-37); the results quantify the oracle's one blind spot, uses inside obsolete code.
- **Slice 8, legacy loading found on DNN Platform:** unresolved analyzer references (a source-generator project never built) made Roslyn's reference and implementation searches throw; the loader drops them and reports what to build. SDK-style .NET Framework projects that import Visual Studio's targets through `$(VSToolsPath)` (WebApplication targets) now load: Roslyn sends every SDK-style project to the .NET SDK's build host, so the loader passes `VSToolsPath` from the installed Visual Studio. Such solutions restore with Visual Studio's MSBuild, as their own build does.
- **Slice 8, evals:** `evals/Farol.Evals` runs each task of `evals/tasks` in a fresh workspace (a fixture copy or a worktree of a pinned repository, restored) through `claude -p`, in two arms that differ only by the plugin, and grades runs with deterministic checks (reply patterns, file contents, changed files, build and test commands, a behavioral script for the VB task). `validate` proves every task with its reference answer or patch before any model call. The pilot showed a fixed cost per session in the Farol arm (loading the skill, then the deferred MCP tools); the skill's description now asks for it only for multi-step work, since the server instructions already carry the basics.
- **Test isolation:** the two test processes run in parallel and design-time loads write `obj/`. Tests that mutate files or run in the MCP test process use temp copies of the fixtures (`FixtureCopy`). Engine tests that load `tests/fixtures` directly share one load per fixture in a serialized collection.
