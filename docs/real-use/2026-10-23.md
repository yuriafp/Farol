# Real use, 2026-10-09 to 2026-10-23

The measurement of the second exit criterion of [spec 001](../specs/001-mvp.md), under the protocol its process log
fixed on 2026-10-08, before the period started: the criterion is met when no blocker is open at the end and the usage
reports show each participant used Farol on real projects on at least six of the ten working days. The developer was
the only participant. The ten working days ran from 2026-10-09 to 2026-10-23; October 12 was a holiday.

## Exit criterion: met, by the developer's decision

| | Measured | Required |
|---|---|---|
| Blockers open at the end | 0 (no issue reported) | 0 |
| Days with use, as the usage report counts them | 7 (10-09, 10-13, 10-14, 10-15, 10-16, 10-21, 10-22) | at least 6 |
| Days on which Farol answered on a real project | 3 (10-09, 10-14, 10-21) | |

The usage report counts a day with calls as a day with use, failed calls included. On 4 of the 7 days (10-13, 10-15,
10-16 and 10-22) every call was the Claude Code plugin's hook failing with `workspace_ambiguous`, so Farol answered
nothing on them; on the other 3 it answered. Counting only the days with an answer, the criterion would not be met.
The developer decided on 2026-10-25 to count it as met on the report's 7 days. The hook's failure and the agents'
use of the tools in Claude Code (findings 1 and 2) are investigated and fixed before the next version.

## Setup

- **Versions:** 0.1.0-alpha.3 on 10-09, 0.1.0-alpha.4 from 10-13.
- **Clients:** Visual Studio 2026 with the Google Antigravity extension (Gemini), with `--usage-log` in the server's
  arguments; from 10-13, Claude Code with the Farol plugin as its only MCP server, with `Farol__UsageLog=true` in its
  settings' environment.
- **Evidence:** the usage log of the period (64 server starts on the working days), its report (below) and the
  repository's issues (none). The test and stress sessions of 10-10 and the two release checks of 10-13 were taken out
  of the log on 10-13, so it holds real use only.
- **Solutions:** the log names a solution only by a hash of its file name. Four appear: `b610ca89` (5 projects),
  `a6a029a6` (7), `4edc5227` (9, Farol itself, loaded on start with no call) and `c50e870c` (55, a fork of an
  open-source game server).

## Findings

1. **The edit hook failed wherever the folder Claude Code opened held more than one solution.** 258 of the 290
   `dotnet_check` calls from Claude Code failed. The hook calls `dotnet_check` with `format=hook` and the edited file,
   without a workspace; the server's root is the folder Claude Code opened, and the workspace is resolved from the root
   before the edited file is looked at. Both repositories the developer worked on in Claude Code during the period hold
   several solutions within the depth discovery searches: a game repository (its engine's `.slnx` and the `.sln` Unity
   generates) and the game server fork (its main solution and three benchmark solutions under `tests/`). Replayed with 0.1.0-alpha.4 on
   2026-10-25, the hook's call answers `Found 2 candidates` and `Found 4 candidates`. On 10-21 the same fork worked,
   because the session had loaded its main solution first and AC-41 kept it: 32 checks, 6 of which handed new errors
   or warnings back to the agent. Nobody noticed the failures during the period: the work went on, and they show only
   in the log.
2. **In Claude Code, agents did not call Farol's tools.** Apart from the hook, Claude Code sessions made 2 calls in ten
   days, both `dotnet_workspace` on 10-21. Navigation, `dotnet_overview` and the rest were not used there, and on 10-19,
   10-20 and 10-23, 23 servers started and none got a call. Claude Code defers MCP tools: the agent sees their names
   and loads a tool before its first call. What the agents used instead is not in the log.
3. **The Antigravity sessions covered every tool.** On 10-09 and 10-14 Gemini called each of the 18 tools, most of them
   once, within minutes, on two solutions of 5 and 7 projects; 47 of the 52 calls answered. They have the shape of a
   tour of the tools rather than of a task. The failures were `path_not_trusted` twice (a root outside the solution's
   folder, which `--root` solved on 10-09), `invalid_argument` twice and `workspace_not_found` once.
4. **Stability and speed held.** No crash. `dotnet_check` p50 16 ms and p95 152 ms; `dotnet_build` p50 6.5 s. The
   55-project solution loaded six times in one session, 13.3 to 16.8 s each, with 3 load errors. The token budget cut
   3 answers (`dotnet_packages`, `dotnet_test`, `dotnet_check`).
